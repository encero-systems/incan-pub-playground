What we ran up against

  • crates.io is straightforward. Its daily response splits newer-version downloads and older-version totals into separate arrays. Both must be summed. We paced requests to meet its one-request-per-second policy.
  • GHCR needs a guarded HTML parser. The public page exposes the total and chart data, but this is not a supported statistics API contract. Missing labels or dates must produce a failed refresh, not zero downloads.
  • A failed source can preserve useful data. Replay tests injected HTTP 429, HTTP 503, changed chart markup and negative counts. Affected sources kept their exact previous records and timestamps; unaffected sources refreshed. An early 429 also stopped further crates.io requests.
  • Repeated snapshots do not add downloads twice. Daily history replaces an observation for the same date and retains earlier dates. Replaying the same input left the snapshot and history unchanged.
  • The released compiler needed small workarounds. Collection logic remains Incan. Existing compiler reports and a reduced follow-up draft are linked in the collector notes.

Before making it nightly

Add bounded retries and backoff, define how partial failures affect publication, and publish the validated JSON and regenerated charts together. For a much larger catalog, evaluate bulk crates.io data. Treat GitHub markup changes as an observable collection failure.

This successful run does not prove long-term reliability. Throttling and outage behavior was verified with offline response fixtures, not live upstream failures.
