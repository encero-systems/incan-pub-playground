COMIC

Canonical Object Markup for Interoperable Crumbs

The text form of a Crumb. It reports what a program contains and what a value holds, in a form people can read and tools can diff.

Design draft from the everything-as-data paper. This is a thought experiment and isn't in any RFC.

.incnHow people write a program
COMICHow anyone reads or exchanges the records as text
CrumbHow the records are stored

Two forms

Almost everything in a file is either a declaration, which says what exists at a path, or a value, which is an instance of a type.

shop.billing.Cents
The edge: where it lives
=
Incan.Newtype { … }
The node: what it is
# A declaration
shop.billing.Invoice = Incan.Model {
    fields { name, type } [
        ("id", Int),
        ("total", shop.billing.Cents),
    ]
}

# A value has no name of its own, so nothing goes on the left
shop.billing.Invoice { id = 1, total = 1200 }

Hashes only cover the block, so moving Cents changes one path and no canonical hash. However much the first form looks like a declaration, a .comic file defines no code, and reading one creates nothing. To keep its values, you crumble it.

A file is a sequence of these with no imports, and declarations sort by path, so reordering source changes nothing. Two or more records of one model in a row print as one table.

Paths

A record has no scope around it, so a path is always absolute: a walk from one of these roots that ends at the real declaration and never at a link. A path reads as one token, because crates-io doesn't lex as an Incan expression.

RootMeansExample

stdThe standard librarystd.primitives.json.JsonEncoder
rustRust's own cratesrust.alloc.vec.Vec
Anything elseA local Loaf, meaningful only inside its projectshop.billing.Cents

This isn't how source spells an import, because the registry identity, the code namespace and the record are three separate things:

# loaf.toml: the key is the code namespace, the string is the identity
spark = { loaf = "apache/spark", version = "3" }
from pub::spark.sql import SparkSession
pub.apache.spark.sql.SparkSession = Incan.Class { … }

An import is a symlink, so it's recorded as a link on the module it adds a name to:

shop.billing = Incan.Module { links = [{ name = "encode", target = pub.crates-io.hex.encode }] }

Kinds

A block's kind is named by its language, because the same word can mean different things: a C enum is open and a Rust one is closed. Each language's block holds that language's own facts, while builtins like Int and Str have no prefix because they're the same type everywhere.

shop.billing.Invoice = Incan.Model { fields { … } […] }
pub.crates-io.serde_json.Token = Rust.Struct { lifetimes = ["a"], fields { … } […] }
pub.c.zstd.ZSTD_bounds = C.Struct { header = "zstd.h", size = 24, align = 8, fields { … } […] }

A path and a kind together make an identity unique, which handles the cases where one name means several things:

# One name, two kinds
pub.crates-io.serde.Serialize = Rust.Trait { … }
pub.crates-io.serde.Serialize = Rust.DeriveMacro { … }

# A repeated trait adoption is a namespace
shop.Reading.Convert[Int].convert = Incan.Function { … }
shop.Reading.Convert[Float].convert = Incan.Function { … }

# An overload lists its parameter types
shop.cast = Incan.Function { overload = [shop.ColumnExpr, Type[Int]], … }

A function is one block holding what callers see and what it does. A closure is the same block with captures and no path, so it sits where it's written, and a Rust or C function has no body, because its body is opaque:

shop.billing.charge = Incan.Function { type = { … }, body = […] }
Incan.Closure { captures = […], type = { … }, body = […] }
pub.crates-io.hex.encode = Rust.Function { type = { … } }

Every nested block has its own hash, and a reference to a function uses the hash of its type, so callers depend only on what they can see and a body change stops at the function. That's the default. A caller that read more than the type, by instantiating a generic, inlining the body, evaluating it as a constant or generating code from it, records that read as its own dependency, so the change reaches it. A hash says what changed, and the recorded reads say who cares.

Markers

Some values can be printed but never read back, so a marker appears in their place and reading one is refused.

Login { user = "ada", password = <secret> }     # Lives only in the running program
Task { timeout = <Duration: 1.5s> }             # Private state, using its own debug text
Encoder { ctx = <ZSTD_CCtx> }                   # A C handle or pointer
Sample { value = <union Value> }                # Only the program knows the active member

Restoring a record that holds a secret

A secret stays in the running program. It's never encoded and enters neither hash. RFC 103 refuses a secret in any ordinary serializer, so a model holding one can't be crumbled or stored, and this marker only ever appears in printed text. Take a login whose password is a SecretStr from RFC 103:

model Login:
    user: str
    password: SecretStr

login = Login(user="ada", password=secret_str("LOGIN_PASSWORD")?)

Printed, that record holds no password at all:

Login { user = "ada", password = <secret> }

So reading that text back can't produce a complete Login on its own. The program has to fetch the secret again, from wherever it keeps it, and hand it over by field name:

# Refused: the text has no password to restore
restored = Login.from_comic(text)?

# The program supplies the field the marker stands for
restored = Login.from_comic(text, password=secret_str("LOGIN_PASSWORD")?)?
  • password= names the field holding the marker. It fills only a marker, so passing user= is refused and a program can't overwrite what the text says.
  • Where the secret comes from is the program's business. Here it's the environment, through RFC 103's secret_str, but COMIC never knows.
  • There are two ?s because two things can fail: fetching the secret, and reading the text.
  • The record gets today's secret, which may differ from the one it held when it was printed. That's on purpose, because a secret can't be restored from a previous state.
  • A marker left unfilled is an error, and is never read as None.

Hashes

A hash covers the value, never the text, so line splits, indentation and key order don't count. A stored record carries three:

HashCoversAnswers
___object_hashEvery stored fieldIs this exactly what was stored?
___canonical_hashThe fields that define the recordIs this the same thing?
___model_hashThe model's own canonical hashWas this written against the same model? Nobody has to assign a version number, but reading a record written against a different model still takes a migration or a compatible descriptor, as RFC 165 requires.
 
model Reading:
    sensor: str
    value: float
    received_at [canonical=false]: DateTime

They go in the record's own block, after its fields, so a stored record is one block named by its type:

sensors.readings.Reading {
    sensor = "a1"
    value = 20.5
    received_at = "2026-11-06T09:00:00Z"
    ___id = "rec_01JC8X…"
    ___revision = "rev_7f3a…"
    ___model_hash = "crumb1:sha256:4be1…"
    ___canonical_hash = "crumb1:sha256:9a2f…"
    ___object_hash = "crumb1:sha256:7c1d…"
}

Three underscores mean the key belongs to the store and not the model, the way two mark a language hook such as __eq__. A model can't declare a ___ name, and RFC 165 stores only Incan models, so a key can't collide with a field; a Rust or C field spelled that way is just a field. No hash covers a ___ key, so a hash never covers itself. ___id and ___revision are the record's RFC 165 identity and revision, and RFC 165 doesn't define their text form, so those two values are placeholders. Two records with equal contents have the same hashes and different identities, and a value that was never stored has no ___ keys.

Fields count unless the model opts them out. A matching hash only finds a candidate, and a typed comparison confirms it, so a collision can't merge two records. A digest beside the data shows that a record no longer matches, but evidence of tampering also needs a signature, or the digest kept somewhere else.

References

A canonical hash never covers a path. Where a block references something, it uses the target's canonical hash, so moving a target moves nothing. The object hash covers the target's path within its Loaf instead, so a move shows there, while publishing doesn't, because the path within the Loaf stays the same.

A hash isn't identity, which is the path, the kind and, for an overload, its parameter types, as RFC 106 requires. Two identical newtypes, shop.a.Id and shop.b.Id, share a canonical hash and remain different types. Repointing a field from one to the other moves no canonical hash, but it moves the object hash and changes an edge, so a tool deciding what to reuse reads those as well.

What counts as the same value

Every hash names its profile as well as its algorithm, as in crumb1:sha256:…, so a hash computed under one set of rules is never compared with one computed under another. A family's codec can lay out its bytes however it wants, because a hash is computed over the profile and not over the stored bytes. These rules are crumb1:

  • -0.0 and 0.0 are different values and hash differently.
  • Every NaN is the one value nan. This profile keeps no NaN sign or payload, so hashing, comparing and reading back all treat them as one value, and a float holding a particular NaN payload doesn't round-trip.
  • Dicts and sets hash in their sorted order.
  • None and Some(None) are different values, while a bare x in an Option slot is the same value as Some(x).
  • Strings aren't normalized, so two spellings of one character hash differently.

Crumbling a file

A .comic file is what you crumble: load into CrumbDB as crumbs, with each value stored under its namespace and queryable there. The namespace is decided at that point, so publishing shop as acme/shop doesn't rewrite the file.

# acme.comic
shop.billing.Invoice { id = 1, customer = "ada", total = 1200 }

# Crumbled into the namespace acme, that record is found under
acme.shop.billing.Invoice

CrumbDB stores records in families and connects them with relationships, so a namespace has to land on those. A path can't simply be a family's name, because moving a type or publishing a Loaf must not rename a family. Crumbling therefore needs a declared, stable mapping from a type to its family, and a declaration's left side becomes a relationship. The CrumbDB paper lists this mapping as an open contract.

Loading follows RFC 165's admission rules and CrumbDB's import checks, which gives the ___ keys a job:

  • A file loads as one transaction, so all of it is published or none of it.
  • An ___object_hash that doesn't match its value is refused.
  • A ___model_hash that differs from the family's model needs a migration or a compatible descriptor, or the record is refused.
  • A reference resolves against the store and the rest of the file, so forward references work. One that finds nothing in either is refused.
  • ___id and ___revision are kept or remapped explicitly.
  • Crumbling the same file twice has to change nothing, and one transaction doesn't give that: a fresh identity on each load would duplicate every record without them. Proposed: such a value takes its identity from the load's import key, its model, its canonical hash and which occurrence it is.
  • A file can't write outside the namespace it's crumbled into, so it can't claim std or someone else's Loaf.
  • A marker such as <secret> is refused, because a stored model can't hold a secret.

A declaration in a file is stored as a description you can query. A program can't import it as a type, which still takes a declaration in source. Writing a file out is an export, so it follows CrumbDB's declared privacy and retention profiles.

  • A lock's paths need versions. One closure can hold two versions of a Loaf, as wasmtime's does with hashbrown. An entry always spells its version, and a reference spells it only when the lock holds two, the same rule that makes a slot use a full path when a short name could mean two types. Outside a lock, a path has no version, because the lock is what says which one. So a file exported from a program has to name the resolved graph its references mean, or a reference to a Loaf held at two versions is ambiguous.
  • The graph's identity needs its own fold. Canonical hashes leave paths out, so two Loaves with the same contents under different names or versions would contribute the same hash, and the root's canonical hash can't serve as the resolved graph identity that RFC 117 asks for. That identity has to bind each entry's exact origin, name, version and dependency edges. RFC 106's closure digest has the right shape: a digest folded over dependencies in identity order.
  • The two hashes still earn their keep. satisfied_by and trust are canonical=false, so when the registry later bakes an asset, the object hash moves and the graph's identity doesn't. An unchanged graph identity doesn't authorize reuse, though: picking a baked asset still checks that asset's own identity, compatibility and trust.

A whole module

from std import web
from rust::hex import encode

type Cents = newtype int[ge=0, storage=u32]

pub model Invoice:
    id: int
    customer: str
    total: Cents

@web.post("/invoices/charge")
@shop.audit.logged("billing")
pub def charge(invoice: Invoice, amount: Cents) -> Result[Cents, str] {
    requires:
        amount > Cents(0)
    ensures:
        Ok(left):
            left <= invoice.total
}:
    return Ok(Cents(invoice.total.0 - amount.0))

pub def reference(invoice: Invoice) -> str:
    return encode(invoice.customer)

Code prints as structure like everything else, because COMIC isn't Incan. A reader needs no Incan parser, and every name is a slot or an absolute path, so a record has no scope. People read a contract in source, which the source field points to, or through a tool that renders the tree as Incan, and that's a view of the record and not a second format.

The edges are the references in those records, so each fact is written once and the graph is an index built from them: the left-side paths, each field's type, and every call and construction.

Decorators and contracts

This round's test found where each of these belongs.

Decorators are part of the implementation

They sit on the function, in order, outside its type. Changing @shop.audit.logged("billing") changes behavior but not what callers compile against, so it recompiles charge and stops there, where putting it in type would recheck every caller for no reason.

  • A decorator that changes the callable's type does reach callers, because type reports what callers actually call. A declared field then holds the written type, and it only appears when the two differ.
  • Capabilities are different because callers rely on them, so RFC 104's caps= shows up as capabilities in type, wherever it was written.
  • Routes can be read without running anything, because they're a query for std.web.post and its literal arguments.

Contracts are part of the type

A contract is a promise to callers, as RFC 111 says, so changing one moves the hash of type and callers are rechecked. A docstring doesn't count toward the hash.

Proofs attach to a hash

RFC 111 stores proof results as facts, and owns what they record. A function can have many proofs, one per obligation, so a proof is a value and not a declaration, and it anchors to the canonical hash of the function it was proved against:

Incan.Proof {
    of = shop.billing.charge
    function = "crumb1:sha256:2c7e…"
    obligation = …
    assumptions = […]
    outcome = Proved
    verifier = …
}

Changing the body, a decorator or the contract moves that hash, so the proof goes stale automatically. Adding a comment doesn't, so the proof can be reused with no solver run, as long as its obligation, assumptions and verifier setup still match. The function's hash already covers the contracts it references, because a reference uses the target's type.

COMIC keeps a declaration's path apart from the fields in its block. TOML has one key space for both, so a method called fields collides with the model's fields. This is the namespace problem again, and the parser refuses it:

One value, one text

This is where YAML falls short. A format can only be canonical if a value has exactly one text and a text has exactly one value, and YAML has neither:

  • Those readings depend on the parser's YAML version. PyYAML and Ruby's parser agree on all of them because both follow YAML 1.1, and YAML 1.2 reads most of them as text. None of the registry's 7,133 feature names or its versions hit this, but stored records hold arbitrary text.
  • No printer gives one value one text. x: 1, {x: 1}, "x": 1, x: !!int 1, x: 0x1 and ? x followed by : 1 all load as the same value. Accepting several spellings isn't the problem, since a COMIC reader also accepts comments, any whitespace and a lone record beside a table. The difference is that COMIC specifies one printer, so each value has one canonical output. A canonical YAML would be a subset and a printer we'd have to define, which is a format of our own anyway.
  • Two kinds at one key are lost silently. With serde.Serialize as both a trait and a derive macro, both parsers kept only the last one and reported nothing. TOML at least refuses it.
  • Tags need a custom loader. The safe loader refuses them, with could not determine a constructor for the tag '!Incan.Model', and a loader that builds objects from tags brings the same risk as pickle. COMIC's reader only ever checks values against a model.

What TOON can't carry

TOON carries the JSON data model, so it can't be what you crumble. Its spec turns 1.0 into 1, -0.0 into 0, and nan and inf into null. Kinds and references are strings, and so are decimals and bytes. In its favor, its encoding rules are close to deterministic, which puts it nearer to canonical than YAML, and its declared lengths let a reader notice a truncated table.

The table COMIC took from it

Uniform rows were COMIC's one real weakness, because every record repeated its path and field names. TOON's table fixes that, so two or more records of one model in a row now print as one:

  • A row is matched by name. The header costs only 5 or 6 tokens, and it means reordering a model's fields can't silently change what old text means.
  • The header carries nested shape. One header describes everything inside a row, so nested records and lists print positionally, and they're still matched by name. A list of two or more records inside a single record is a table too, and so is a dict of records.
  • A cell is never skipped. A row writes None for a missing optional and [] for an empty list, and a column is left out of the header when every row could leave that field out: an optional that's None in every row, or a collection that's empty by default in every row.
  • Each row is still one record. It has its own hashes, and stored records fit with ___id and the hashes as columns. A table is only layout, so no hash covers it, and it loads naturally into one family when crumbled.
  • A writer can still append. A reader accepts a lone record or a second table at the end of a file, and the formatter merges them, which keeps one value, one text.

Wide data: Adobe

Adobe Analytics data feeds, formerly Omniture, are about as wide as tables get. The column names here are real, from Adobe's public column reference: 987 current columns and 199 retired ones, 1,186 distinct names in all. The rows are generated, because no real feed is public, so the fill rates are assumptions, and gzip results depend on the generated values.

Field identities pass

None of the 1,186 names collide at 6 bytes, or even at 4, and the chance that any two would is about 1 in 400 million. At 2 bytes, 13 of them do, which rules that length out on one real model. Listing all 987 current columns takes 5,922 bytes as identities against 10,986 as names, once per frame, which is under half a percent of the 500 rows below. Older feeds are remembered at 1,358 columns, and at that width the chance is still about 1 in 300 million.

The identity list could also fix a known weakness of Parquet and ORC on wide tables. A 2023 evaluation of both formats found that metadata parsing grows almost linearly with the number of columns, even when a query reads only 10 of them, because their footers can only be decoded in sequence, and it says future formats must allow random access to per-column schema. Proposed: keep the list sorted, so a reader finds one column among 1,358 by binary search, in about 11 steps over fixed 6-byte entries, with nothing to parse. A micro-benchmark puts one lookup at about 40 ns over the packed list, or 32 ns once a reader has widened it to 64-bit words, which it does once per shape in about half a microsecond. Nothing was compared against Parquet's footers.

  • What the larger raw form buys is position. Reaching one value in Parquet means decompressing and decoding a page of up to 20,000 rows, while here its position can be computed and read directly from uncompressed bytes. That's a property of the layout, and nothing was timed.
  • Parquet's defaults leave a lot on the table here. Dictionaries stop at 1 MB and fall back to plain values, so lifting the limit takes the same Snappy file from 51.9 MB to 32.2 MB, and the published file behaves the same at 52.1 MB. So a dictionary shouldn't have a small fixed cap, and an encoding is better chosen per column.
  • It's still a big step from Protobuf: 72% smaller raw and 55% smaller after gzip, in the same comparison of blocks against one stream that favors Protobuf.
  • The limits: this is one row group of one dataset, with no nulls, so null levels are untested. Parquet also has skippable pages, a page index and statistics that this layout doesn't, and it's a real format where this is not. Iceberg stores its data in Parquet, ORC or Avro, so it has no file-size test of its own.
  • Field identities: 105 names, no collisions even at 4 bytes, and a list of 630 bytes.

A crumb against Protobuf

Crumb has no implementation yet, but its shape is clear: a crumb is the binary form of a value as it sits in memory. So its size can be estimated from a Rust program using RFC 121's types, with money and times as i64:

  • A literal dump can't work. Memory holds addresses, so two equal values matched in only 17,793 of their 20,000 inline bytes. They couldn't share a hash or be loaded back, and RFC 165 rules out depending on addresses, padding or byte order.

What Parquet and Iceberg teach

Neither is a text format, so they say little about COMIC's notation. They have a lot to say about the two layers beneath it: Parquet about Crumb, and Iceberg about how records change over time.

From Iceberg

  • Match fields by ID, not by name or position. Iceberg's data files are read by field ID, so renaming and reordering can't misread old data. This is the biggest lesson here. Protobuf gets schema evolution by writing a tag on every value; a Crumb frame lists its fields' identities once, and old readers can still skip what they don't know. The details are below.
  • Write down which changes are allowed. Iceberg permits adding, deleting, renaming and reordering fields, and widening int to long, float to double or a decimal's precision, and it forbids the rest. RFC 165's "compatible descriptor" needs the same list.
  • Separate two kinds of default. An initial default fills old rows written before a field existed, and is fixed once set. A write default fills new rows, and can change. Both belong to the descriptor, which keeps COMIC's text free of defaults.
  • Keep the name out of the data. A catalog maps a name to a table's metadata, so renaming rewrites nothing. That's the shape of the mapping crumbling needs from a namespace to a family.
  • Trunders have good company. Iceberg reserves metadata columns such as _file and _row_id, along with a range of field IDs, and its row IDs survive a row moving between files, as ___id should.
  • Deletes are a solved shape. Its deletion vectors are a bitmap per data file, which is worth reading before deciding how COMIC spells a tombstone.

From Parquet

Columns compress far better than rows, and a table has the shape to use them. This is the same 100 orders, in encodings written for this test. None of them is Crumb, and the payload flatters them, because it repeats a few product names and customers:

  • A table in text could be columns in Crumb. The text stays in rows, because that's what people and models read. If a crumb is what's in memory, a table's crumb would look more like Apache Arrow, the in-memory columnar layout that's built to be shared without decoding, with Parquet as its compressed cousin on disk. A lone record has no columns to exploit, so Crumb would need both layouts.
  • Definition and repetition levels are how Parquet flattens nested lists and optionals into columns, and they keep None apart from a missing parent. A columnar Crumb has to answer the same question.
  • Statistics let a reader skip. A footer holding the schema and each chunk's location is written last, so a writer needs only one pass, and a reader goes straight to the columns it wants.
  • Logical types over physical ones. A decimal is an integer with its scale in the schema, the same idea as Int { storage = u32 }.

Crumb matches fields by identity

The question is how a reader finds a field in bytes written by an older or newer version of the model. There are four answers, and Crumb takes the last:

A reader finds a field byReordered fieldsA renamed fieldA new field, old readerCost
PositionMisread, silently if the types matchFineBreaksNone

Iceberg assigns its IDs in table metadata, but Crumb can't copy that, because RFC 168 requires it to work outside any store, in files and messages. Incan already has the concept, though: RFC 085, as amended in the open RFC batch and not yet on main, says a field keeps its identity through renamed_from, and that a rename without it is a new identity. So the identity is a short hash of the field's earliest name, computed by the compiler, with nothing new in source.

It's the first 6 bytes of the SHA-256 of that name, as RFC 165 now says in a change not yet on main. It only has to differ from every field its own model has ever had, because a frame already names its model, by a hash of the model's earliest path such as shop.billing.Invoice, so it needs far fewer bits than a UUID, which has to be unique everywhere. Two names that collide in one version of a model are a compile error, and the fix is to name the new field differently. A dropped field that collides with a later one is invisible to the compiler and would misread old values silently, so the width has to make that negligible on its own: a model that has ever had 1,000 field names has about a 1 in 560 million chance at 6 bytes, against 1 in 8,600 at 4. Stored, an identity is 6 raw bytes, and printed, it fits in 9 characters:

A scan of the Incan and IncQL repos found 1,612 models with 3,613 fields, at most 20 in one model, and nothing collides even at 4 bytes, inside a model or among all 809 distinct names. By arithmetic, a model that has ever had 100 fields has about a 1 in 57 billion chance of a collision.

# Version 1
model Invoice:
    id: int
    customer: str
    total: int

# Version 2: reordered, one rename, one new field
model Invoice:
    total: int
    id: int
    buyer [renamed_from="customer"]: str
    note: Option[str]

A frame written by version 1 lists the identities of id, customer and total, then its rows. A version 2 reader matches them to id, buyer and total, and reads note as None, with no migration and nothing misread. A version 1 reader of a version 2 frame does the same in reverse and skips note, which a reader going by names can't do across a rename.

  • The model hash becomes part of a fast path. Reading straight from the bytes takes more than a matching model hash, because one model can have different codecs, row or column layouts, compression and format versions. The frame's codec profile has to match too, its framing has to validate, and alignment and lifetime have to hold. If the model differs, the identities decide what it can use and it copies those values across, and a required field that's missing is refused.
  • A record's canonical hash is keyed by identity, so renaming or reordering fields moves no record's hash, though the model's own hash still moves.
  • COMIC's text keeps using names. Identities only exist in Crumb, and the text's tables already match rows by name.

The list costs 108 bytes for the order payload, 18 fields at 6 bytes each, once per frame. These are the costs:

  • Small messages pay. 108 bytes is little against 100 orders and a lot against one, which already takes 336 bytes as a dump against Protobuf's 195. Leaving the list out where the reader can look a model up by its hash avoids that, but it needs somewhere to look.
  • A name that returns is the same field. Dropping a field doesn't erase its values from existing data, so they read again when the name returns and their type still fits, and additive changes are preferred anyway. A field with a new meaning needs a new name. Parquet files read by column name behave the same way. Iceberg goes the other way, giving a re-added column a new ID from its table metadata, and it calls reusing a name by accident "un-deleting" a column. That takes a table to hold the IDs, which a crumb doesn't have, so if accidental reuse needs preventing, that's CrumbDB's job at the family level and not Crumb's.
  • A forgotten renamed_from looks like a drop and an add. A required field then fails loudly, but an optional one quietly reads as None. A lint comparing against the previous model could catch it.
  • The earliest name has to stay in source. After retire_in, RFC 085's lint now suggests removing only the lifecycle facts and keeps the earlier name, because removing it would change the identity. Actually removing it counts as dropping one field and adding another. This is what lets a frame decode on its own after its model has moved on.
  • Rename chains keep one identity, because a list in renamed_from is in the order the names were used, earliest first.
  • Type changes fail loudly. The identity covers only the name, and the frame says what type each field was written as, so a field changed from address: str to address: Address keeps its identity, and an old value is refused by name instead of skipped. Only the listed safe widenings, such as i32 to i64 or str to Option[str], read without a migration.

The positional code nodes in COMIC's text aren't helped by this, since they have no header.

Why it's concise

Six rules keep the text small. The first five make it smaller, and the last only changes how it reads. A hash covers the value and not the text, so the notation moves no hash.

  • Code nodes print positionally. They're enum variants, and ( ) is already how a variant prints. It stays structure: there's no Incan parser involved, and names are still slots or absolute paths.
  • A wrapper with one field goes. body = Block { statements = […] } becomes body = […].
  • Empty lists, sets and dicts are left out where the model declares empty as their default.
  • A block's name is left out when its slot allows only one kind. Registry says nothing inside registry. Root declarations and slots with several kinds keep their names.
  • Two or more records of one model print as a table, whose header carries nested shape.
  • No commas between fields on separate lines. Incan's own blocks in RFC 096 separate entries by newline. Commas stay in lists and on one line.

A contract shows the biggest difference:

With named fields 
requires = [
    Compare {
        op = Gt,
        left = Parameter { slot = 1, name = "amount" },
        right = Construct { of = shop.billing.Cents, arguments = [0] },
    },
]
Now 
requires = [Compare(Gt, Parameter(1, "amount"), Construct(shop.billing.Cents, [0]))]

Together they took a function from 54 lines and 876 bytes to 21 lines and 617, and the whole module from 92 lines and 1,510 bytes to 45 lines and 1,128.

What they cost

  • Positional values depend on order. Reordering a variant's payload silently changes what old text means, where named fields don't. A stored record's ___model_hash catches that, but a loose file has nothing to catch it.
  • A fragment no longer says what it is: Project(x, 0) needs the model to name 0, and so does a bare {. Reading already needs the model, but a person skimming a file doesn't have it open.

Which hash does what

RFC 106 is already the normative source for declaration identity and digests, and RFC 124 builds on them. Two questions need two answers:

  • Has this declaration changed? RFC 106 answers that with a semantic digest over checked meaning, including resolved targets and ownership facts, a closure digest over dependencies, and a separate documentation digest. COMIC should print those. The rules on this page about a function's type hash and what callers read should defer to them and to the compiler's own dependency edges.
  • Is this stored record the same value, and can I read it? That stays with the canonical, object and model hashes, because RFC 106 doesn't cover values. A model hash has to leave paths out, or moving a type would force a migration, and RFC 106's digest includes resolved targets, so it can't do that job.
  • One rule to borrow. RFC 106 keeps the previous digest projection readable, so an improved normalization doesn't look like a change to every declaration. A hash profile such as crumb1 needs the same.

Which tree a body prints

The function bodies on this page print a resolved tree, such as Parameter(1, "amount"), and they were written without looking at RFC 160 or RFC 161. Incan plans three trees:

TreeWhat it isFor COMIC
std.vocab surfacePublished models and enums that vocabularies read and writeStable, but syntax-shaped, so names aren't resolved and "who calls this?" has no edge to follow
Checked bodyThe compiler's own representationResolved, but private and unversioned
SCIR inspection viewEvery surface normalized, versioned and read-onlyResolved and versioned, and where all surfaces meet

Proposed: SCIR's inspection view. RFC 161 rules out a writable core and commits to inspectable facts, which is what COMIC already is. Since every surface meets there, "same tree, same hash" holds by construction, and much of 0.7's new syntax, such as chained comparisons, normalizes away instead of adding COMIC nodes.

The costs are real. A SCIR body also spells copies, moves and loans, so it will be larger than the sizes measured on this page, by an amount nobody has measured. An improved ownership planner moves digests unless a schema version accounts for it. And RFC 161 has no release assigned yet, so COMIC at 1.0 would depend on one.

The native boundary is data

Decided: the contract for handing a program to the native compiler, the proposed std.compiler.native, is a versioned data schema shaped like COMIC and not a builder API, so it grows additively. Builds pass it in memory or as crumbs, and text is for reading, tests and diffs. A file earns no trust, so it goes through the same checks as anything else. COMIC can be compiled in the way LLVM IR can, and Incan stays the one language people write.

Still open

  • Which tree a body prints, and how the hashes divide with RFC 106, as proposed above.
  • An import key: how a value without ___id keeps one identity across loads, and how two identical rows stay two records.
  • How a program supplies secrets for a nested field or for a table of records, where one password= can't say which marker it fills.
  • CrumbDB has families and relationships but no namespaces, so crumbling needs a declared, stable mapping from a type to its family. The CrumbDB paper lists this among its open COMIC contracts.
  • CrumbDB's model needs three spellings COMIC doesn't have yet: a deleted record, since RFC 165's revision can be a tombstone; a reference to another record, by its logical subject or an exact revision; and the snapshot a file was written from.
  • A table can lose or gain a whole row unnoticed, as TOON's validation test shows. A file's snapshot is the natural place to catch it: a hash over the file's values notices a changed or missing row, where a row count only notices the count. The same snapshot should name the resolved graph the file's references mean.
  • RFC 165 and CrumbDB bind a family to a schema version that a project writes by hand, as schema_version=1. A model hash could replace that label, which would change the API but not the migration rule.
  • A decorator that changes a callable's type depends on the unsettled question of runtime versus compile-time decorators (#2479).
  • Hashing across references relies on hashing a cycle as one group, which hasn't been designed in detail.
  • Debug information: a comment shifts line numbers that panic locations report, so spans have to refresh without counting as a code change.
  • Crumb needs a real layout before its numbers mean more than an estimate, including whether APIs get a more compact form than a store.
  • Size at scale hasn't been measured. The small module above takes about 2.4 lines for each line of source.
